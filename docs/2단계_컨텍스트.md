## 2. AI 구조 — 맥락 분석: 안내문 읽기 + Jev 1차, 교차 분석 2차 (확정 11/16, 용어 정리 11/22)
- 판별 내용: **QR 안내문의 목적 ↔ 실제 접속 페이지의 목적이 일치하는가** (참/거짓)
- **Jev AI 현황 (11/20)**: 선결제 $5·API 키 발급 완료, 대회 규모에서 한도 걱정 없음. ~~연동은 팀원 담당~~ → **연동 완료 (11/20 밤, `app/jev.py`·`app/context.py`)**
  - (11/20 갱신) 참/거짓만이 아니라 **선택지별 확률을 준다** (예: 일치 0.01 / 불일치 0.99 / 판단불가 0.00). 입력 토큰만 과금(100만 토큰당 $0.042), 출력 무료, 응답 약 0.3초
  - 질문: 선택지 `일치 / 불일치 / 판단불가` 고정 질의. 문구 5종 비교 결과 **영어 지시 + 한국어 데이터(V3)**가 가장 정확 → `eval/jev_prompt_results.md`
  - 판정: 불일치 확률 **0.8 이상 강한 신호(40점), 0.5 이상 약한 신호(확인 권장 10점)**. 기준값은 `settings.json`의 `context` (실제 안내문 사진으로 재확정 예정)
  - 오타 내성: 안내문 읽기 오타가 약 25% 섞여도 판정 유지 → `eval/jev_typo_results.md`, `eval/demo_eval_results.md`
  - 확률이 있으므로 2차 호출 조건 "Jev 결과 애매"(0.5~0.8)를 쓸 수 있음
- **1차 (맥락이 있을 때 항상)**: 카메라 전체 프레임/업로드 이미지 → **Gemini 멀티모달로 안내문 글자·항목 추출** → 페이지 정보와 함께 **Jev AI에 고정 질의** → 불일치 시 **강한 신호**
  - Jev 입력은 글자이므로 안내문 읽기가 Jev의 입력을 만드는 앞 단계임
  - (11/20 갱신) Jev는 사진도 받을 수 있으나 공식 문서상 실험 기능 → **Gemini 안내문 읽기가 실패했을 때(요청 한도·서버 오류)만 대체 수단**으로 Jev에 사진을 직접 넣음. 덧붙인 스티커도 같은 호출에서 확인
- **2차 (조건부, 교차 분석)**: **Gemini 멀티모달**이 원본 사진과 접속 페이지를 함께 보고 판단. 1차는 사진을 정해진 항목으로 줄이면서 나머지 정보(금액·날짜·연락처·로고·배치)를 버리고, 페이지를 보기 전에 읽으므로 둘을 직접 비교하지 못함 → 2차가 이것을 맡음. 호출 조건 예: 안내문 글자를 거의 못 읽음 / Jev 결과 애매 / 글자 없이 로고·그림 위주 / 덧붙인 스티커처럼 배치로 드러나는 단서
  - **(11/22 팀 결정·구현) 2차의 존재 의의 = 규칙(1차·정책 검사)이 다루지 않는 추가 문제를 AI가 자유롭게 찾는 것.** AI가 1차 검사 정책을 기준으로 삼으면 결과가 같아지므로, **이미 검사한 항목은 AI 검사에서 제외**한다. 대회 점수(AI 창의성)를 위해 자율성을 유지하되, 멘토 의견(하네스)을 반영해 최소 기준은 둔다:
    - 관점 힌트만 제공(금액·요금 / 기관·사업자 / 날짜·기간 / 연락처·계좌 / 유도 행위 / 표기·디자인 + 기타), `settings.cross_check.perspectives`
    - 답 형식 고정(관점·설명·안내문 근거·페이지 근거·심각도), 인용 근거가 원문에 없으면 프로그램이 제외(환각 방지)
    - 호출 조건: 안내문을 읽어 목적 비교를 한 경우(포스터형)만. 요청 한도에 걸리면 생략
    - 구현: `app/cross_check.py`. 시연 확인(11/22): 사례 1~5는 추가 발견 없음(목적 차이는 1차가 이미 잡음), **요금만 다른 정산 페이지(1차 '일치')에서 금액 어긋남을 찾아냄** → "1차 통과, 2차가 잡음" 시연 사례로 쓸 수 있음
    - 처음엔 AI가 목적 불일치를 '유도 행위'로 바꿔 다시 보고 → "목적 차이를 다른 말로 다시 보고하지 말 것" 지시 추가 후 해결
    - ⚠ **미결정(11/23 멘토링에서 피드백 후 확정): 점수 반영 방식** — `display_only`(표시만, 임시 기본값) / `weak_capped`(약한 신호, 상한 15점) / `with_other_signals`(다른 위험 신호가 있을 때만). 설정값 하나로 바꿀 수 있게 세 가지 모두 구현해 둠
    - 확장 아이디어: AI가 자주 찾는 유형을 사람이 검토해 1차 규칙으로 승격 (규칙이 계속 늘어나는 구조)
  - 구현 순서: **1차 먼저 완성 → 1차가 놓치는 사례 확인 후 2차 추가**, 시간이 부족하면 확장 계획으로 돌림
  - 2차도 **하네스 안에서 동작**: 허용 분석 종류와 출력 형식(JSON 스키마)을 미리 고정, 자유 분석 금지
  - 목적은 해설이 아니라 **추가 분석을 통한 결론 도출** (중간보고서의 "상세 근거 제시" 표현은 이 의미로 정정)
- 2차를 나중에 붙이기 쉽도록 **지금 미리 할 것**: ① 원본 이미지를 파이프라인 끝까지 유지 ② 결과 스키마에 "이미지 분석" 칸을 비워 두기(값 "미실행") ③ 2차 호출 조건을 설정 파일로 분리
- **맥락이 없으면 맥락 분석을 생략하고 정책 검사만 수행 (합의 11/20)** — QR만 확대 촬영, URL 직접 입력 등. 결과에는 "맥락 정보 없음" 표시
  - "QR만 찍었는지" 판단 방법: **QR이 프레임에서 차지하는 면적 비율 + QR 주변 글자 유무**로 거른다 (⚠ 기준값 미확정, 샘플로 정할 것)
- 결과 근거에 양쪽을 나란히 표시 (예: "안내문: OO시 주차요금 결제 / 실제 페이지: 무관한 신규 도메인의 결제 화면")
- 하네스 원칙 유지: AI는 프로그램이 정한 질의에만 답하고, 검사 규칙을 스스로 판단하지 않음
- 결정 대응 예방 수칙: "출처가 불분명한 QR 주의" 대분류의 소분류로 들어감
- 안내문 읽기 도구: ~~미선정~~ → **Gemini 멀티모달로 확정 (11/20)**. 기존 키 사용, 서버 부담 없음(API), 합성 안내문 77장 한국어 인식률 99.8%·안내 목적 100% (`eval/ocr_results.md`). 사진은 긴 변 1024px로 줄여 보내고, 사진이 올라오는 순간 미리 읽기 시작. 오픈소스 OCR 도구(PaddleOCR·EasyOCR 등)는 Render 무료 서버 메모리로 구동이 어려워 제외
- ⚠ 미결정(멘토링 후): 1단계의 Gemini 페이지 사칭 판별을 2단계에서 유지할지 (유지 쪽이 자연스러움 — 탐지율 40→80.7%의 근거 기능), 규칙이나 Jev 질의로 대체할지
- ~~⚠ 미결정: `page_purpose`가 없을 때 처리~~ → **(11/20 구현) 페이지 제목·본문 일부(600자)로 대체**. 접속 실패(HTTP 400 이상)면 오류 화면을 페이지로 오해하지 않도록 맥락 비교 생략
- (11/20 구현) 맥락 생략: 사진이 없거나(URL 직접 입력) Gemini가 안내문 글자를 거의 못 읽으면(8자 미만·readable=false) 비교 생략, 결과에 사유 표시. ⚠ 팀 합의안(QR 면적 비율·주변 글자 유무)과 방식이 다름 — 지금은 QR만 찍은 사진도 Gemini를 한 번 호출함
- **(11/22 구현) 생략 기준 확정: 2단계 결합** — ① 사진이 올라올 때 QR 면적 비율 계산, `context.skip_qr_ratio`(임시 0.35) 이상이면 Gemini 호출 없이 생략(결과 'QR만 찍힘') ② 애매하면 기존 Gemini 읽기 결과(8자 미만·readable=false)로 생략. 측정: 시연 포스터 7~9%, 글자 있는 QR 이미지 18~22%. ⚠ 실제 'QR만 가까이 찍은 사진'으로 기준값 재확인 필요

## 3. 실행 환경·비용
- 모델·API는 설정으로 교체 가능하게 유지
- Gemini는 무료 티어가 있으나 무료/유료의 차이는 주로 호출 한도·데이터 처리 방식이고, 성능은 모델 등급에 좌우됨. 무료 티어는 입력이 구글 제품 개선에 쓰이므로 **실제 사용자 이미지는 보내지 않고 시연용 가짜 이미지만** 사용 (또는 유료 티어 사용). 무료 한도는 줄어드는 추세라 사용 모델의 현재 한도를 직접 확인
  - **(11/20 결정) 시연 전용 운영**: 카메라 사진이 Gemini 무료 티어로 전송되므로 배포 주소는 공개하지 않고 시연용 포스터(`demo/case*.png`)만 사용. README에 명시
  - 검사 1번에 Gemini 2번(안내문 읽기 + 페이지 판별) → 설정 한도(분당 10건)에서 분당 약 5번 검사까지 여유. 넘으면 안내문 읽기는 Jev 사진 판정으로 대체
- 이미지 입력 단가는 장당 약 $0.001 수준(모델별로 다름)이라 대회 규모에서 비용 부담은 작음
- **멘토 제안 "API 대신 Claude Code 로컬 구동"**: 2026-06-15부터 `claude -p`·Agent SDK 호출은 구독 한도가 아닌 **별도 월간 크레딧**(Pro $20 / Max 5x $100 / Max 20x $200)을 소모하므로 "무료"가 아님. 지원받은 Max 등급과 조건은 Anthropic 지원 문서로 확인 필요. 결과 일관성(결정적 출력 설정 부족), 응답 속도, 로그인된 노트북 필요(고정 주소 배포와 충돌), 개인 사용 가정 약관 문제가 있음
  - **방침**: 기본은 API 유지, 로컬 Claude Code는 시연용 선택지로 남김. 쓴다면 사전 리허설 필수
- ⚠ 미결정(멘토링 후): 모델 성능 평가 — 미탐 약 26건(135건 × 19.3%) 원인 분류, 같은 365건 스냅샷으로 더 강한 모델 재측정 (중간보고서 발전 계획 ④ "모델별 품질·속도·비용 비교" 이행)
- **시연 방식 확정 (11/20)**: Render **고정 주소 배포** 사용, ngrok 안 씀 (설정: `render.yaml`, 방법은 README)
  - 무료 요금제는 일정 시간 접속이 없으면 **잠들어 첫 접속이 느림** → **시연 직전에 미리 접속해 깨워 둘 것**

- **카메라 권한 주의**: 사용자가 한 번 "차단"하면 웹앱은 **다시 권한을 물을 수 없음**(브라우저 정책, 브라우저 설정에서 직접 풀어야 함)
  - 안내 문구·카메라 자동 시작 방식 변경을 시도했으나 **기존 방식 유지**로 되돌림
  - **시연 전 시연용 폰에서 카메라 권한을 미리 허용**해 둘 것
- 기능은 기존 웹앱과 거의 같고 바뀌는 건 설치·실행 경험(홈 화면 아이콘, 주소창 없는 전체 화면, 앱 이름·스플래시)
- 발표 방향: PWA로 핵심 가치(찍는 즉시 판정)를 검증 → 이후 네이티브 앱 패키징, 기본 카메라·공유 메뉴 연동으로 확장. 시연은 홈 화면에 설치한 폰 화면으로
- 흐름은 1단계와 동일: 카메라 첫 화면 → 바로 결과 → 판정·수칙·행동 안내 → 상세보기
- 상세보기에 **AI가 읽은 안내문 + 맥락 비교 결과** 추가

## 5. QR 분석기 확장
- **QR의 의도·목적을 먼저 분류** (결제 / 웹사이트 이동 등) → 목적별 검사 항목 적용
- 결과를 **계층형**으로:
  - 대메뉴: 범죄 유형 (일반인도 아는 대표 용어, 예: 피싱)
  - → 범죄별 검사 카테고리 (큐싱 예방 수칙 위계와 연결)
  - → 세부 검사 항목
- 백신 결과 로그처럼 처음엔 위험도만, 카테고리를 타고 들어가면 세부 사유
- 범죄 유형 확장 후보: 1단계에서 제외했던 불법 도박·성인 사이트, 사기 쇼핑몰 등 콘텐츠 분류
- ⚠ 미결정: 전체 검사 항목을 나열하고 탐지 항목만 체크 vs 탐지된 항목만 표시
