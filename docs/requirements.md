# QR 피싱 분석기: 분석 로직 및 화면 개선 요청

## 0. 작업 전 확인
- **웹 서비스**로 구현한다. 대상 페이지 접속, 도메인 정보 조회, 스크린샷, AI 호출은 브라우저가 아닌 **서버(백엔드)**에서 처리한다.
- 현재 프로젝트 구조, 기술 스택, 이미 구현된 검사 로직을 먼저 파악하고 요약해 줘. (새로 시작하는 경우 적절한 스택을 제안하고 확인받은 뒤 진행)
- 이전 과제(TrustRoute, Android URL 파밍 검사 앱)의 화이트리스트와 검사 설계를 재사용할 예정이니, 해당 자료를 주면 반영해 줘.
- 아래 요구사항을 기존 코드에 맞춰 적용해 줘. 구조를 크게 바꿔야 하면 바꾸기 전에 계획을 먼저 보여줘.
- 마감이 11/6(중간보고서)이므로 **7. 구현 우선순위** 순서대로 진행하고, 단계마다 동작 확인 후 다음 단계로 넘어가 줘.

## 1. 입력 방식
- **카메라 QR 스캔**: 브라우저/기기 카메라로 QR을 실시간 인식
  - 카메라 화면에 "안내문까지 함께 비춰 주세요" 같은 짧은 안내 표시
  - QR을 인식한 순간의 **카메라 화면 전체(프레임)를 이미지로 저장**해 분석 요청에 함께 보낸다. (QR 주변 안내문 맥락 분석용, 6절 참고)
- **파일 업로드**: QR이 포함된 이미지 파일 업로드, **드래그 앤 드롭** 지원
  - 이미지 안에 QR이 여러 개면 모두 추출해서 선택하게 하기
  - 업로드한 원본 이미지도 맥락 분석용으로 함께 보낸다.
  - QR을 못 찾으면 명확한 안내 메시지 표시
- **URL 직접 입력**
- 어떤 방식이든 QR에서 URL을 추출한 뒤 같은 분석 파이프라인으로 보내기

## 2. 화면 흐름
- 중간 처리 과정(단계별 진행 화면)은 따로 보여주지 않는다.
- URL/QR이 입력되면 **바로 분석 결과 화면으로 전환**한다. (로딩 중에는 간단한 스피너 정도만 표시)

## 3. 분석 구조: 피싱 분석(메인) + 기타 주의사항(부가)
이 프로젝트는 **피싱 분석기**다. 판정은 피싱 분석 하나에 집중하고, 피싱이 아니라고 무조건 안전하다고 단정하지 않도록 기본적인 유해 요소는 부가 점검으로 알려준다.

| 구분 | 판단 대상 | 결과 |
|---|---|---|
| 메인: 피싱 분석 | 사용자를 속여 정보·금전을 빼내려는 사이트인지 | 안전 / 주의 / 위험 (유일한 판정) |
| 부가: 기타 주의사항 | 피싱은 아니지만 확인이 필요한 점 | 별도 판정·점수 없음, 해당 항목만 나열 |

### 3-1. 기타 주의사항 (추가 구현 부담이 적은 항목만)
- **악성/원치 않는 소프트웨어 DB 등재**: Google Safe Browsing을 호출할 때 위협 유형에 MALWARE, UNWANTED_SOFTWARE를 함께 요청해 결과를 그대로 사용 (별도 API 호출 없음)
- **실행 파일 다운로드 유도**: 최종 도착 URL의 확장자(.apk, .exe 등) 또는 응답 헤더 Content-Type으로 확인
- **연결 보안**: http(암호화 안 됨), 인증서 오류·만료·도메인 불일치

### 3-2. 판정 반영 규칙
- 기타 주의사항은 피싱 판정을 바꾸지 않는다. 걸린 항목이 있으면 판정 옆에 "주의사항 N건" 표시만 붙인다.
- **예외**: 악성코드 DB 등재(확정 신호)는 종합 판정을 "위험"으로 올린다.
- http는 단독으로 판정에 영향을 주지 않는다. 주의사항으로 알리고, 4-3 조합 규칙에 해당할 때만 피싱 점수에 반영한다.

### 3-3. 이번 범위에서 제외
- 불법 도박·성인 사이트, 사기 쇼핑몰 판별 등 콘텐츠 분류는 구현하지 않는다. (2단계 고도화 후보)

## 4. 피싱 점수 계산 방식
단순 총점 합산이 아니라 **신호를 등급별로 나누고, 안전 신호로 감점**한다.

### 4-1. 위험 신호 등급
- **확정 신호**: 점수와 관계없이 즉시 "위험"
  - 피싱 DB 등재 (예: Google Safe Browsing SOCIAL_ENGINEERING, PhishTank/OpenPhish 목록)
- **강한 신호** (높은 배점)
  - 유명 브랜드 유사 도메인(타이포스쿼팅, 예: navver.com)
  - 신규 등록 도메인(예: 30일 미만)
  - 단축 URL이 전혀 다른 도메인으로 리다이렉트
  - IP 주소로 된 URL
  - 브랜드·도메인이 일치하지 않는 로그인/결제 입력 폼
  - **AI 사칭 판별 결과**: 페이지가 특정 서비스를 사칭하고 실제 도메인과 불일치 (6절)
  - **AI 맥락 불일치 결과**: QR 안내문 목적과 실제 페이지 목적이 불일치 (6절, 2단계)
- **약한 신호** (낮은 배점, **합계 상한 있음**)
  - http, 비정상적으로 긴 URL, 과도한 서브도메인, 특수문자·인코딩 문자 과다, 파라미터 과다 등
  - **약한 신호만으로는 아무리 많이 걸려도 최대 "주의"까지만** 나오게 상한 적용

### 4-2. 안전 신호 (감점)
- 신뢰 상위 사이트 목록 포함 (예: Tranco 상위 목록, 기존 TrustRoute 화이트리스트 재사용)
- 오래된 도메인 (등록 후 수년 경과)
- 정상 인증서 (유효한 HTTPS, 도메인 일치)
- 감점은 확정 신호를 상쇄하지 못한다. (DB 등재 사이트는 화이트리스트에 있어도 위험)

### 4-3. 조합 규칙 (상황별 가중)
단독으로는 약하지만 같이 나타나면 위험한 조합을 별도 규칙으로 처리한다.
- **http + 로그인/비밀번호/결제 입력 폼** → 강한 신호로 격상
- http지만 입력 폼이 없는 일반 정보 페이지 → 약한 신호 유지
- **신규 도메인 + 브랜드 유사** → 추가 가중
- **단축 URL + 최종 도착지가 신규 도메인** → 추가 가중
- 규칙은 코드에 하드코딩하지 말고 설정 파일(JSON 등)로 분리해서 쉽게 추가·수정할 수 있게 한다.

### 4-4. 임계값
- 안전/주의/위험 경계 점수는 설정 파일로 분리한다.
- 정상 URL(신뢰 상위 사이트) 약 100개와 피싱 URL(PhishTank/OpenPhish) 약 100개로 점수 분포를 확인하는 **검증 스크립트**를 만들어 줘.
  - 출력: 정상 사이트 오탐률, 피싱 탐지율, 점수 분포
  - 정상 사이트 오탐을 최소화하는 방향으로 임계값을 조정
  - 결과 수치는 발표 자료에 쓸 수 있게 표로 정리
- 검증은 실시간 접속이 아니라 **4-5에서 수집한 저장본(스냅샷)**으로 돌린다. 같은 데이터로 다시 돌려도 같은 결과가 나와야 한다.

### 4-5. 검증 데이터 수집 스크립트
피싱 사이트는 몇 시간~며칠이면 사라지므로, 수집 시점에 분석에 필요한 정보를 모두 저장해 둔다.
- **피싱 URL**: OpenPhish 무료 피드 등 공개 피싱 피드에서 최신 URL을 받아온다. (사용 가능한 피드와 이용 조건을 먼저 확인)
- **정상 URL**: Tranco 상위 목록 + 국내 주요 사이트(브랜드 목록의 공식 도메인)에서 추출한다.
- URL마다 다음을 함께 저장한다.
  - 수집 일시, 출처, 정답 라벨(피싱/정상)
  - 리다이렉트 경로와 최종 URL, 응답 헤더
  - HTML 원문 (크기 제한)
  - 도메인 정보(생성일 등), 인증서 정보
  - Safe Browsing 조회 결과
- 접속 실패한 URL은 제외하고 실패 사유를 기록한다.
- 이미 저장한 URL은 다시 수집하지 않고, 여러 번 실행해 데이터를 누적할 수 있게 한다.
- 수집 시 7절 보안 요구사항(파일 다운로드 금지, 시간 제한, 상호작용 금지)을 똑같이 지킨다.
- 분석 로직은 실시간 접속 결과와 저장본을 같은 형식으로 입력받을 수 있게 설계한다.

### 4-6. 사칭 대상 브랜드 목록
- 유사 도메인 탐지(4-1)와 AI 사칭 판별(6-1)이 공통으로 쓰는 **브랜드 → 공식 도메인 목록**을 설정 파일(`brands.json` 등)로 둔다.
- 형식 예: `{"name": "국민은행", "aliases": ["KB국민은행", "KB"], "category": "은행", "official_domains": ["kbstar.com", "kbcard.com"]}`
- 팀에서 준비한 목록 파일을 주면 그대로 사용한다.

## 5. 결과 화면
- 맨 위: **피싱 판정** (안전/주의/위험, 색상으로 구분) + 해당 시 "주의사항 N건" 표시
- **판정 근거**: 위배된 논리정책을 근거로 함께 제시
  - 영향이 큰 순서로 정렬, 핵심 근거 2~3개는 바로 보이게, 나머지는 펼쳐보기
  - 일반 사용자가 이해할 수 있는 문장으로 표시 (예: "도메인이 5일 전에 생성됨", "naver.com과 비슷한 도메인")
  - 안전 신호(신뢰 사이트, 정상 인증서 등)도 "안전 근거"로 함께 표시
- 판정 근거 아래: **기타 주의사항** 섹션 ("피싱은 아니지만 확인이 필요한 점"), 걸린 항목이 없으면 섹션 숨김
  - 예: "암호화되지 않은 연결(http)", "앱 설치 파일(.apk) 다운로드로 연결됨"
- 점수 숫자는 크게 노출하지 않는다. (상세 보기에서만 표시)
- 분석한 원본 URL과 최종 도착 URL(리다이렉트 후)을 함께 표시
- AI가 판단한 페이지 목적 표시 (스크린샷 기능이 켜져 있으면 접속 페이지 미리보기 썸네일도 표시)
- **맥락 비교 영역**: 안내문 목적 vs 실제 페이지 목적을 나란히 표시 (1단계는 자리만 만들고 "2단계 제공 예정" 또는 "맥락 정보 없음" 표시)

## 6. AI 분석
AI는 결과 해설용이 아니라 **규칙으로 판단할 수 없는 "의미" 판단**에 쓴다. URL 구조·도메인 정보처럼 규칙이 더 정확한 것은 규칙으로 처리한다.

### 6-1. 페이지 사칭 판별 (1단계 구현)
단계적으로 구현한다.

**① 기본: HTML 텍스트 분석 (먼저 구현)**
- 서버에서 대상 페이지 HTML을 가져와 다음을 추출해 LLM에 텍스트로 전달한다.
  - 페이지 제목, 본문 텍스트(길이 제한), 입력 폼 항목(비밀번호·카드번호·인증번호 등 필드 종류)
  - 이미지 파일명·alt 텍스트, favicon, 폼 제출 대상과 주요 링크의 도메인
- 이 단계는 헤드리스 브라우저 없이 동작해야 한다.

**② 추가: 스크린샷 분석 (헤드리스 브라우저 세팅이 되면 추가)**
- 서버 환경에서 헤드리스 브라우저(Playwright 등)가 문제없이 동작하면, 스크린샷을 찍어 텍스트와 함께 멀티모달 LLM에 전달한다.
- 목적: 로고·안내 문구가 이미지로만 들어가 HTML에 브랜드명이 없는 피싱 페이지 탐지, 결과 화면의 페이지 미리보기 제공
- 스크린샷 기능은 설정으로 켜고 끌 수 있게 하고, 꺼져 있거나 실패하면 ① 결과만으로 진행한다.
- 세팅에서 막히면 무리하지 말고 ①로 1단계를 마무리한다.

**공통**
- 무료 이미지 입력이 가능한 Gemini API(Google AI Studio)를 기본 후보로 하고, 무료 한도(분당·일일 요청 수)를 넘지 않도록 한다.
- LLM 출력은 구조화된 JSON으로 받는다. 예:
  ```json
  {
    "claimed_service": "국민은행",
    "page_purpose": "인터넷뱅킹 로그인",
    "requested_info": ["아이디", "비밀번호", "OTP"],
    "official_domain_guess": "kbstar.com",
    "confidence": 0.85,
    "reason": "제목과 본문에 국민은행 명칭, 비밀번호·OTP 입력 폼 존재"
  }
  ```
- 사칭 대상의 공식 도메인과 실제 도메인이 다르고, 개인정보·금융정보를 요구하면 **강한 신호**로 피싱 점수에 반영한다.
- `page_purpose`는 6-2 맥락 일치 분석에서 재사용하므로 항상 저장한다.

### 6-2. QR 안내문 맥락 일치 분석 (2단계 구현, 1단계는 구조만 준비)
이 프로젝트의 핵심 차별점이다. 실제 큐싱은 정상 안내문 위에 가짜 QR 스티커를 덧붙이는 경우가 많으므로, **QR이 붙어 있던 곳의 안내 목적과 실제 접속 페이지의 목적이 일치하는지** 확인한다.
- 입력: 카메라 전체 프레임 또는 업로드 원본 이미지 (QR 주변 안내문 포함)
- LLM이 이미지에서 안내 맥락을 추출한다. (예: "OO시 공영주차장 요금 결제", "OO카페 메뉴 주문")
- 6-1의 `page_purpose`와 실제 도메인을 비교해 불일치하면 **강한 신호**로 반영한다.
- 근거에는 양쪽을 나란히 표시한다. (예: "안내문: OO시 주차요금 결제 / 실제 페이지: 시청과 무관한 신규 도메인의 결제 화면")
- 맥락이 없는 경우(QR만 확대 촬영, URL 직접 입력)는 분석을 건너뛰고 "맥락 정보 없음"으로 표시한다. 피싱 판정은 그대로 진행한다.
- **1단계에서는** 프레임 저장, 저장된 이미지를 분석 요청에 포함하는 흐름, 결과 화면의 표시 자리까지만 만들어 둔다.

### 6-3. AI 호출 조건과 반영 원칙
- 피싱 DB 등재(확정)이거나 신뢰 상위 사이트면 AI를 호출하지 않는다. **규칙만으로 판정이 애매한 경우에만 호출**해 API 비용을 줄인다.
- AI 판단을 그대로 최종 판정으로 쓰지 않고, 피싱 점수의 **신호 하나**로 반영한다.
- 결과 근거에 "AI 판단" 출처를 표시한다.
- AI 호출 실패나 시간 초과 시 "AI 분석 불가"로 표시하고 규칙 기반 결과만으로 판정한다.
- API 사용료가 별도로 드므로, 저렴한 모델을 기본으로 쓰고 모델명은 설정으로 바꿀 수 있게 한다.

### 6-4. 사용하지 않는 것
- 안내 문구·문자의 사회공학 패턴(긴급성, 보상 미끼 등) 분석은 효과 대비 비효율적이라 구현하지 않는다.

## 7. 공통 요구사항
- 분석 대상 페이지 접속은 서버에서만 한다. HTML 수집 시 응답 크기·시간 제한을 두고, 파일은 내려받지 않는다(헤더로 형식만 확인).
- 헤드리스 브라우저를 쓰는 경우 격리된 환경에서 실행하고, 파일 다운로드 차단, 입력 폼 제출 등 상호작용 금지, 접속 시간 제한을 둔다.
- 외부 API(Safe Browsing, WHOIS 등) 실패 시 해당 항목은 "확인 불가"로 표시하고 나머지 분석은 계속 진행
- API 키는 환경변수로 관리, 코드에 직접 넣지 않기
- 각 검사 로직은 함수/모듈 단위로 분리해 개별 테스트 가능하게 하기

## 8. 구현 우선순위
### 1단계 (11/6 중간보고서 마감)
0. 검증 데이터 수집 스크립트(4-5)를 가장 먼저 만들어 바로 수집을 시작 (구현하는 동안 데이터가 쌓이도록)
1. URL 입력 → 피싱 점수 계산(신호 등급, 약한 신호 상한, 안전 신호 감점, 조합 규칙) + 기타 주의사항 점검 → 결과 화면(근거 표시)
2. AI 페이지 사칭 판별 ① HTML 텍스트 분석(6-1) 연결
3. QR 이미지 파일 업로드 + 드래그 앤 드롭
4. 카메라 QR 스캔 + 전체 프레임 저장
5. 임계값 검증 스크립트 및 결과 표 (AI 사칭 판별 적용 전후 비교 포함)
6. (여유 있으면) 6-1 ② 스크린샷 분석 추가

### 2단계 (고도화)
- QR 안내문 맥락 일치 분석(6-2) 완성
- 1단계에서 스크린샷 분석을 못 넣었다면 추가
- 1단계 검증에서 놓친 피싱 유형을 분석해 보완
